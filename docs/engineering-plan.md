# Engineering timeline: stabilize guided capture, then validate live recording

**Planning baseline: 29 September 2026; status reconciled with the published preview on 13 October.** Capacity is **one full-time engineer**, approximately 30–32 implementation hours plus 8–10 hours of tests, investigation, and documentation each week. Dates below are the original conditional targets, not a refreshed delivery forecast. They assume Windows 11 x64 hardware, a Windows 10 build 19045 compatibility machine, WPA, administrator elevation, eight pilot participants, and an available Windows CI runner.

The source and v0.4.0-preview.1 executable are public as an **experimental open-source utility**. Source 02770d2 passed 116 tests and all main/tag CI steps on Windows Server 2025; the anonymously downloaded bundle passed the local desktop workflow, and its source ZIP built independently. These results close the missing exact-revision CI gate for that preview. Windows 10 capture recovery, independent Windows 11, privileged helper attack/trust validation, usefulness and repeated performance acceptance remain open. See [current checkpoints](checkpoints.md) for the current engineering work and [preview evidence](verification/public-preview-20261013.json) for the frozen release results.

## Critical path and prerequisites

1. **Engineer:** retain a Windows workflow result for the exact source revision. Source 02770d2 has successful full main and tag runs. Each subsequent code revision needs its own result; earlier passes do not validate later changes.
2. **Engineer with administrator access:** complete shipping-helper capture-to-report checks on Windows 10 and Windows 11. Both profiles and lifecycle cases passed Windows Server CI, but the 2 October Windows 10 Resources save exceeded its 60-second timeout; FileActivity was not attempted. Profile-details inspection alone is insufficient.
3. **Engineer:** repair any capture/coverage failure, then reconcile analyzer correctness and performance against real recordings.
4. **Engineer plus pilot participants:** complete security, Windows 11, scale, and usability acceptance. Only then decide whether to promote a stable release and expand recording scope.

Independent offline-parity and query profiling can proceed while Actions or elevation is blocked. The capture acceptance gate cannot. Reserve Windows 11 test access and recruit pilot users in Week 0 so scheduling does not begin after engineering work finishes.

The original profile-naming hypothesis was followed by successful server start/save checks for both shipping profiles; profile inspection alone had been insufficient. Desktop save failures still require their own reproduction and repair. Keep capture commands scoped to the uniquely owned WPR instance; retain the existing ownership and recovery rules.

The work packages below total roughly **40–54 engineering days**, leaving integration/review capacity in the 12-week window and two weeks of contingency. The critical path is native capture → measured coverage → parity/performance → security and Windows 11 → pilot → release. Adding an engineer helps independent profiling and UI tasks, but does not remove the evidence gates.

The CPU-weight gate cannot be closed by merely renaming the metric. If native equivalence requires a different estimator, version the behavior and rerun comparisons. If a recording lacks enough sampling metadata, leave CPU percentage unavailable for that recording. Do not silently relax the 1% tolerance or discard observations to improve speed.

## Acceptance ledger for a stable release

| Gate | Evidence to retain |
|---|---|
| **Native capture** | Helper version, profile, Windows build, requested and observed providers, start/stop/cancel transcript, source hash, ETL size, loss count, and selected evidence. Test automatic and manual stop, cancellation, helper/UI death, a second named WPR instance, and low disk. Store sensitive ETLs locally. |
| **Parser correctness** | WPA/TraceProcessing equivalent-filter tables for event counts, completed bytes, CPU weight, process lifetime, and interval boundaries. Document any definition mismatch. |
| **Performance** | Cold and warm import, first and repeated queries, partial-edge latency p95, paging, derived-file size, and peak worker memory on a named 12-logical-processor/approximately-32-GiB reference machine plus Windows 11 machine. Include failed runs and thermal/IO context. |
| **Security** | Negative cases for IPC and filesystem inputs, ownership recovery, no arbitrary SQL/commands, same-account elevation, and distribution-location trust. |
| **Product** | Eight-user scorecard: two everyday, two developer, two power, two IT/investigation users; at least six succeed within two minutes and find supporting evidence. Preserve baseline workflow times and misinterpretations. |
| **Distribution** | Locked dependencies, dependency notices, clean-source rebuild, self-contained extracted ZIP on a machine without SDK, no accidental ETL inclusion, versioned analysis cache, and verified asset SHA-256. |

[GitHub-hosted Windows runners are Windows Server VMs](https://docs.github.com/en/actions/reference/runners/github-hosted-runners), so a successful Actions run does **not** replace testing the declared Windows 11 desktop baseline. If CI infrastructure is unavailable, run the same scripts locally, retain results, and keep the current-revision remote gate open.

## Conditional Stage 3: live recorder

The original eight-week estimate below covers an eventual persistent/background recorder and its acceptance, conditional on correctness and usefulness. Manual bounded in-memory observation and saved investigations have since been implemented; these do not close the 24-hour recorder gate. The original 11 January–5 March 2027 dates are conditional planning targets, not a current commitment.

| Window | Deliverable | Gate |
|---|---|---|
| **11–22 Jan** | Define distinct source IDs, clocks, coverage and provenance for one-second Windows API snapshots versus ETL. Prototype low-volume lifecycle ETW and trace-local lifetime mapping through authorized collector IPC. | API counters are labeled by meaning; no snapshot is passed off as recorded physical disk I/O or retroactively added to an ETL. |
| **25 Jan–5 Feb** | Implement CPU/memory/I/O snapshots, bounded rolling persistence, retention manifests, crash restart, manual incident preservation, and reported loss. | Known retained duration, bounded storage, safe disk-full behavior; no silent gaps or unbounded cumulative writes. |
| **8–19 Feb** | Build current-resource and recent-history views connected to the deterministic evidence model. High-volume file/Registry tracing is temporary and explicit. A buffering-only ETW session needs a separate live delivery path because [ETW buffering mode does not deliver real-time events](https://learn.microsoft.com/en-us/windows/win32/etw/logging-mode-constants). | Responsive UI with source, timestamp, units and coverage on each displayed value. |
| **22 Feb–5 Mar** | Run 24-hour idle and workload benchmarks, measure slowdown, writes, memory, retention and event loss. | Experimental targets: <1% total-machine CPU idle, <2% during representative workloads, <512 MiB headless memory, <100 MiB/hour telemetry writes. Report actual values and failures; do not claim these budgets in advance. |

Stages 4–6 remain conditional: temporary stacks/Registry/scheduling analysis after measured costs; service/security and Sysmon only with source-specific identities; optional natural language only over deterministic queries with cited evidence and explicit cloud opt-in. Drivers, eBPF, temperatures, exhaustive heaps, and automatic remediation remain outside this plan absent a demonstrated requirement.

## Weekly operating rule

Every Friday update a shared evidence ledger with gate, fixture/source hash, machine and OS, command or UI path, expected/actual result, issue owner, and next experiment. At each two-week review choose **proceed**, **repair**, or **defer**. Do not replace a failed run with a newer successful average. If CI runner access, elevation, Windows 11 hardware, or pilot recruitment is unavailable, continue independent work but move the dependent milestone rather than calling it complete.
